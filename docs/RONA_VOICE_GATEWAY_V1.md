# RONA Voice Gateway V1

Status: fail-closed technical foundation
Owner approval: 2026-08-23

## 1. Purpose

RONA Voice Gateway connects an external PSTN/SIP telephone line to the existing RONA Trade AI staff contour without weakening fixed-role identities, least privilege, IAM, client access gates, or the audited network-only internal communication rule.

Target path:

`PSTN / corporate number -> SIP/telephony provider -> OpenAI Realtime SIP -> RONA Voice Gateway -> reception/router boundary -> fixed-role AI employee contour -> audited network coordination -> authoritative admin workflow when required`

The telephone number is an external communication channel. It is not an identity provider and does not create Portal User, client binding, agent binding, contract access, or any other authority.

## 2. Fixed-role boundary

Allowed business roles behind the voice contour remain:

- `AI-OPERATIONS-DIRECTOR`
- `AI-FINANCE`
- `AI-LEGAL`
- `AI-MARKET-ANALYST`
- `AI-RAIL-LOGISTICS`

`AI-SYSTEM-ADMIN` is not a telephone business-routing target.

The reception/router boundary has no inherited FINANCE, LEGAL, MARKET_ANALYST, RAIL_LOGISTICS, OPERATIONS_DIRECTOR, SYSTEM_ADMIN, IAM, contract, publication, settlement, or client-binding authority.

A future role bridge must select exactly one applicable fixed-role contour for a business interaction and must not expose all role write authorities to one shared voice model.

## 3. Identity and client-data policy

Caller phone number, caller-provided name, caller-provided email, spoken company name, SIP header, address-book match, or prior call history MUST NOT automatically become authoritative user identity.

General public/business information may be handled within the applicable approved projection. Client-specific contracts, payments, documents, deal state, private prices, bank data, access state, or other protected data require the same authoritative identity mapping and access gates as the non-voice LK contour.

Ambiguous or missing identity evidence is fail-closed. The call may collect a request for follow-up, but protected data is not disclosed.

## 4. Internal communications

All internal follow-up generated by a call must use the audited RONA network coordination contour. Internal email is prohibited for handoffs, assignments, approvals, internal documents, or internal notifications.

Email remains permitted only for external communication or for a request that originally arrived by email.

Voice events do not themselves authorize business/system mutations. Required mutations continue through their existing authoritative workflows.

## 5. Data retention defaults

V1 foundation defaults:

- call metadata: private technical storage;
- raw webhook payload: not stored; only SHA-256 payload hash and minimal event metadata are stored;
- audio recording: `DISABLED`;
- transcript: `METADATA_ONLY`;
- secrets/tokens: never stored in call metadata, audit metadata, client-facing output, or logs;
- QA identities/internal diagnostics: never exposed to callers or client-facing LK.

Recording can only be enabled after an approved jurisdiction/consent/retention policy and a separate audited configuration change.

## 6. Database objects

`portal_private.voice_gateway_control`

Singleton fail-closed control. A fresh installation is disabled for inbound and outbound calls and cannot enable either direction unless provider, OpenAI Realtime, and model execution states are `READY`.

`portal_private.voice_calls`

Private call lifecycle metadata. Phone fields are private. `routed_role` cannot be `SYSTEM_ADMIN`. Identity verification requires an explicit authority mapping reference.

`portal_private.voice_call_events`

Append-only technical event trail. Update/delete is rejected by an immutable trigger.

`portal_private.voice_outbound_requests`

Audited outbound request queue. Every request requires an existing non-QA `ai_coordination_records.record_id`, a fixed business role, an E.164 destination, purpose, and idempotency key. The initial implementation records requests as `BLOCKED`; it does not fabricate provider delivery.

All V1 voice tables are revoked from `anon` and `authenticated`.

## 7. Edge gateway

Function: `rona-voice-gateway`

Routes:

- `GET /health` — non-secret service liveness only;
- `GET /admin/health` — authenticated ADMIN readiness view;
- `POST /openai/webhook` — OpenAI webhook ingress; raw body signature verification is mandatory before processing;
- `POST /admin/outbound/request` — authenticated ADMIN audited request registration; no provider call is sent in V1 foundation.

The public OpenAI webhook route is fail-closed when `OPENAI_API_KEY` or `OPENAI_WEBHOOK_SECRET` is absent. Incoming Realtime SIP calls are rejected while the voice activation gate is not fully ready.

Required activation environment flags are deliberately absent by default:

- `RONA_VOICE_ROLE_BRIDGE_READY=true`
- `RONA_VOICE_PROVIDER_ADAPTER_READY=true`

No database state alone can bypass those code-level gates.

## 8. External prerequisites

The following real external inputs are required before live telephony can pass:

1. Corporate telephone number and SIP/PSTN provider selected for the required country/number type.
2. Provider account and real API/SIP credentials, stored only as protected runtime secrets.
3. OpenAI API project with Realtime/SIP capability and a server-side `OPENAI_API_KEY`.
4. OpenAI webhook configured to the Voice Gateway and protected `OPENAI_WEBHOOK_SECRET`.
5. Provider routing from the corporate number to the OpenAI SIP destination or an approved provider adapter.
6. Role-bridge implementation/test proving that a shared reception boundary cannot inherit multiple fixed-role authorities.
7. Human/reserve failover destination and successful failover test.
8. If recording is requested: approved legal/consent/retention policy before enabling recording.

Credentials, phone numbers, provider state, routing status, or webhook delivery must never be invented when evidence is absent.

## 9. Activation gates

### Gate A — FOUNDATION

PASS requires:

- database migration applied;
- edge gateway deployed;
- public health reachable;
- admin health authenticated;
- all inbound/outbound controls remain disabled;
- no secret leakage;
- no Portal User/client binding can be created from a phone number;
- outbound request without ready provider is persisted as `BLOCKED`, not simulated as sent.

### Gate B — INBOUND_TEST

PASS requires real evidence:

- real corporate/SIP number;
- provider routing configured;
- OpenAI API key + webhook secret provisioned;
- verified OpenAI `realtime.call.incoming` webhook;
- role bridge ready;
- one real inbound call accepted;
- fixed-role routing and identity fail-closed behavior verified;
- human failover tested;
- no protected data or internal diagnostics exposed.

### Gate C — OUTBOUND_TEST

PASS requires real evidence:

- provider outbound adapter implemented and credentials provisioned;
- outbound call originates from an existing audited network coordination record;
- idempotency prevents duplicate dialing;
- caller ID policy is valid;
- call outcome is written to the private immutable event trail;
- internal follow-up remains in the network contour.

### Gate D — PRODUCTION_READY

Only after Gates A-C pass may `enabled`, `inbound_enabled`, and `outbound_enabled` be activated through an authoritative admin workflow. Production activation must preserve all existing AI STAFF PROTOCOL and LK authority gates.

## 10. Current expected blocker

Until real provider/number credentials and OpenAI Realtime credentials are provisioned and the fixed-role voice bridge is tested, the correct production state is:

- telephony/provider: `BLOCKED`;
- OpenAI Realtime: `BLOCKED`;
- voice model execution: `BLOCKED`;
- inbound: disabled;
- outbound: disabled.

This is an intentional security state, not a failed simulated integration.
